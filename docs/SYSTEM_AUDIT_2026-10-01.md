## 缺陷位置與修復方式

### A01：KMS 匯入的帳號隔離

先前確實已修正同類型問題：`v26.9.30.2` 保護買賣頁 CSV 與 JSON 還原，`v26.9.30.5` 再補齊投資設定頁的交易、出入金、股利 CSV 及股票字典 Excel 四個入口。這些修正仍在目前程式中。本項是**尚未套用相同保護的「知識庫首頁 → 批次匯入筆記（JSON／CSV）」入口**，不是先前修正失效或被移除。原清單應明確區分這個剩餘範圍。

位置：`src/pages/kms/KMSHome.tsx:763`、`:806`、`:818`。匯入沒有在 `file.text()` 前捕捉 session，每一筆重新呼叫 `userCol`／`userDoc` 取得當下使用者。切換帳號造成元件卸載，也不會取消已在執行中的 async handler。

建議沿用投資設定匯入的 `captureUserSession()`：讀檔前固定帳号，讀檔後、每筆寫入前後檢查 session，路徑全部使用該 session；帳號變動立即停止，回報原帳號已確認完成的筆數。這不改動密碼保存或正常登入持續性。

### A02：新增交易與同時操作

位置：`src/pages/invest/Trades.tsx:518`–`:556`；伺服器預檢只在 `editingId` 存在時呼叫。`oversellWarning` 使用頁面 state，背景同步不能保證儲存瞬間 state 已更新。

重現執行實際 `handleSave`，替換資料庫 I/O 及 React state 接收端；兩次新增都使用相同舊庫存，寫入共 1,200 股，伺服器預檢次數為零。最後共用 `assertNoNewOversells` 確認合併帳本缺股。

建議所有新增／編輯／刪除入口統一驗證目前帳本。只補「新增前 getDocs」可縮小風險，仍無法阻止兩個真正同時的操作；完整修復需讓全部寫入者共用原子驗證或帳本 revision 的衝突重試機制，涵蓋匯入與還原。不要自動調整使用者原始成交或出入金日期。

### A03：CSV 的指定庫存沖抵

位置：`src/lib/dayTradeCsv.ts:3`、`src/pages/invest/InvestSettings.tsx:727`、`src/pages/invest/Trades.tsx:786`。CSV 有保存當沖配對，卻沒有保存 `inventoryMatches`；兩個交易匯入入口也未讀取這個欄位。

R06 用實際 CSV 配對序列化工具及 `calcPositions` 比較指定第二批庫存與遺失指定後的結果。匯入後既有 JSON 保護與單筆資料驗證，無法恢復根本沒有匯出的欄位。

建議 CSV 新增指定庫存沖抵欄位並驗證買入 ID、股數及歷史可用量。JSON 完整備份原樣保存此欄位，本項問題針對 CSV；修復後也不應自動重算或改寫所有正式帳務。

### A04：Google 刪除衝突

位置：`src/lib/googleCalendar.ts:463`–`:470`，`:615`–`:620`。一般遠端更新有尊重 pending 標記，但遠端取消分支先無條件安排本機刪除。後續 transaction 只確認筆記沒有在本次同步期間又變動，並不阻止既存 pending 修改被刪除。

建議本機有 pending 修改時保留事件並顯示衝突，讓使用者選擇接受刪除或保留修改，再安排後續同步。Google 正常刪除其他事件的行為仍應保留，並增加遠端取消、本機修改、重複同步與斷線重試的回歸測試。

### A05：原型債券 ETF 證交稅

位置：`src/lib/calc.ts:31`–`:34`、`:116`；`src/components/TradeSettlementDetails.tsx:16`。系統只有一般股票 0.3% 與所有 ETF 0.1% 兩種自動稅率。

依[財政部稅務入口網](https://www.etax.nat.gov.tw/etwmain/tax-info/understanding/tax-q-and-a/national/securities-transaction-tax/taxation-scope/7r3MjNB)，符合規定的上市／上櫃債券指數股票型基金受益憑證自 2017-01-01 至 2026-12-31 停徵。[證交所投資人說明](https://investoredu.twse.com.tw/pages/TWSE_InvestmentQA.aspx?ID=11)指出原型債券 ETF 與槓桿／反向型的適用差異，不能把所有名稱有債券的商品一律設為零。

建議以商品分類及交易日期決定預估稅率，保留元大實際費稅覆寫；同步修改預估變現淨值、試算及費稅說明。2027 年以後是否延長須另依生效法規確認，不能把修法草案當成已生效規則。沒有讀取正式交易資料，因此本次不知道使用者是否已交易受影響商品。

### A06：交易 CSV 的實際費稅

位置：`src/pages/invest/Trades.tsx:756`–`:757`、`:772`–`:773`；對照 `src/pages/invest/InvestSettings.tsx:340`–`:344`。買賣頁直接重算費稅，沒有讀檔案中的「手續費」或「交易稅」。檔案同時提供收付時，被後續一致性驗證擋下；沒有提供收付時，改用預設費稅寫入。

建議兩個入口共用同一份匯入資料轉換器：有效原始費稅優先、缺值才估算，並明確區分零元與未填。券商實際金額與估算不同時應能核對原因。

### A07–A09：KMS 匯入可靠性

位置：`src/pages/kms/KMSHome.tsx:777`、`:798`–`:821`；共用 CSV 解析器在 `src/lib/csv.ts:15`。

- **空 URL：**僅在有值時加入欄位或明確使用有效空值；SDK 拒絕與網路失敗應列為失敗，顯示原因，不能全部算為略過。重現用實際 Firebase SDK 的 `WriteBatch.set` 在離線下驗證資料，不曾呼叫 SDK commit。
- **跨行 CSV：**使用可處理整份 CSV 的解析器，讓引號狀態跨行延續；各匯入入口統一處理換行、逗號、跳脫引號及 BOM，保留正文及備註。
- **重試去重：**固定本次匯入的 row ID／匯入識別及來源帳號，對寫入結果不明確的項目中止並允許安全重試，提供已有來源 ID 的去重。避免用只比標題的規則誤刪真正不同筆記。

## 安全改善及適用界線

### S01：前端第三方用量金鑰

`src/lib/fugle.ts:3` 和 `src/lib/gemini.ts:4` 使用 `VITE_` 設定直接呼叫供應商。正式建置掃描結果為：

| 設定名稱 | 本機有設定 | 本機 dist JS 含該設定值 |
|---|---|---|
| VITE_FUGLE_API_KEY | 是 | 是 |
| VITE_GEMINI_API_KEY | 是 | 是 |

本次沒有輸出設定值、沒有將其加入證據檔，也沒有用金鑰發起供應商付費請求。此確認針對本機產物；正式站 bundle 本次未比對。

建議兩種 API 完整改走 Firebase 登入驗證的後端代理，加入用量上限及快取，前端移除用量金鑰；完成搬移後再處理現有公開金鑰的輪替。這個調整可沿用裝置的登入狀態，不需要要求使用者每次輸入密碼。

### S02：依賴更新

本次連線 npm 官方 registry 執行兩份獨立的 `npm audit --omit=dev --json`，僅查詢公告，沒有修改套件或 lockfile。

| 套件範圍 | moderate | high | critical | 受影響套件項目總數 |
|---|---:|---:|---:|---:|
| 根目錄 | 37 | 7 | 1 | 45 |
| firebase-functions | 8 | 1 | 0 | 9 |

這些是套件與相依傳播項目數，**不是 54 個獨立可利用的系統漏洞**；兩份報告也有重疊。不能從此數字推定正式站可被遠端入侵。

- `xlsx@0.18.5`：`InvestSettings.handleImportDict` 直接解析使用者選擇的 Excel。[SheetJS 官方 CVE-2024-22363 公告](https://cdn.sheetjs.com/advisories/CVE-2024-22363)說明 ReDoS 的受影響版本及修復來源；npm 舊 `xlsx` 套件不能靠一般 `npm audit fix` 解決。應評估官方新版或替換解析工具，兼顧原有匯出相容性及大檔處理。
- `@tiptap/core@3.29.2`：[維護者安全公告](https://github.com/ueberdosis/tiptap/security/advisories/GHSA-cp6q-959q-f8rh)列出 `mergeAttributes` 問題及 patched version 3.30.4。公告也明說標準固定 schema 不會讓任意 JSON 自動成為可利用攻擊；本次沒有證明本系統的 XSS 利用路徑。建議整組 Tiptap 一起升級並驗證圖片、連結、富文字保存及還原。
- 其他受影響項目包含 React Router、grpc、websocket-driver、Firebase Admin 的相依套件及解析工具。React Router 公告有多項針對 SSR／RSC，本系統使用 Vite SPA，不能直接套用所有攻擊結論。Fubon 本批使用的行情模式，也應與套件內其他服務路徑分開判斷。

建議做單獨依賴更新批次，逐一判斷能否更新及呼叫路徑，完成功能驗證後再由使用者決定部署。不要直接執行強制升級。
