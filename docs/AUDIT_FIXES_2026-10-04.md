## 1. 現在是一個怎麼樣的系統

Symbiosis 是整合 **個人投資帳務、研究知識庫、行事曆／任務與 AI 閱讀助理** 的管理系統。React／TypeScript 前端提供手機與電腦介面，Firebase 保存帳務、筆記與行程，Netlify Functions 處理驗證後的外部服務呼叫，Firebase Functions 處理搜尋索引等維護工作。

投資核心依交易、確認股利與出入金，計算 FIFO 持倉、現金、融資負債及淨資產；績效以資產快照與外部資金流計算。元大月結單辨識與資料健康檢查協助核對帳務。KMS 保存研究內容，透過標籤、連結、圖譜與搜尋整理；行事曆將研究與日常工作轉成事件／任務；AI 協助檢索、閱讀與討論。

主要帳務仍以單一元大帳戶、台股與單幣別為範圍。外國報價屬研究能力，不表示已具備完整海外交割與外幣帳務。AI 的投資資料仍是有限摘錄，不可取代共用帳本計算或原始月結單。完整模組與資料流程見修正前報告第 2 節。

## 2. 本批已完成的修正

| 編號 | 已修正的行為 | 驗證重點 |
|---|---|---|
| R01 股利認列 | 歷史損益、年度月表與熱圖共用實領判斷，排除預告、尚未到付款日的收入；以實際付款日歸屬月份／年度 | 預告不加總；跨月付款出現在付款月；現金與報表口徑一致 |
| R02 XIRR | 年度與區間使用同一套 365 天算法；無解／不適用顯示缺值及原因 | 不把求解失敗顯示成 0%；相同資料得到相同結果 |
| R03 歷史區間 | 使用指定日期已確認收盤的淨資產端點與實際出入金；不以今天股價重估歷史；不信任舊手填起始金額 | 缺端點、重複端點或品質不足時停止該區間績效計算 |
| R04 最大回撤 | 改用排除外部資金流影響的淨值指數計算峰谷回撤 | 不再拿從零起算的已實現損益當資產回撤；資料斷點不顯示假 0% |
| R05 KMS 匯出 | 載入筆記時固定帳號 session，正文批次、舊正文讀取、下載與延遲下載都核對同一帳號 | 載入後／匯出中切換帳號會停止並要求重新載入；不混合 A 標題與 B 正文 |
| R06 融資配股 | 新增「配股中的融資股數」，統一配股後的庫存、成本、借款與償還計算；CSV 保留此欄位與 0 值 | 已確認 1,000 融資股＋100 融資配股，賣完 1,100 股後庫存及本金清零；成本與負債不被重複加減 |
| R07 快照品質 | 保存估值時間與 closing／intraday／manual-unverified 品質；自動快照等待供應商確認的最終收盤；不能以盤中擷取降級已確認收盤 | 收盤不能只靠時鐘猜測；舊快照不自動視為精確收盤；績效要求可信收盤資料 |
| R08 股利年份 | 年度明細納入已實領股利年份，即使沒有賣出股票 | 純領息年度仍有明細，沒有交易成本／勝率時顯示不適用 |

另外修正年度表原先「全部股利＋已實現損益」除以「已賣股票成本」的混用分母。持有未賣股票的股利不再被塞進該交易成本比率。現在分開顯示 **已實現報酬率** 與 **帳戶年化報酬**；後者由該年度可用的收盤淨資產端點與外部資金流求 XIRR，沒有足夠資料則顯示缺值。

主要程式位置：`src/lib/calc.ts`、`performanceReturns.ts`、`snapshot.ts`、`portfolioSnapshot.ts`、`kmsData.ts`；投資頁 `YearReview.tsx`、`HistoryPnL.tsx`、`AssetTrend.tsx`、`Dividend.tsx`、交易／對帳呼叫端，以及 `KMSExport.tsx`。

## 3. 修正後的公式與資料品質規則

| 指標／資料 | 現在採用的規則 |
|---|---|
| 淨資產 | 持倉市值＋帳務現金－融資本金。現金股利已進現金，不再額外加一次 |
| 已實現報酬率 | 已實現交易損益÷對應已售批次成本；沒有適用成本則缺值 |
| 帳戶 XIRR | 期初淨值為負、入金為負、出金為正、期末淨值為正；365 天年化。帳內買賣與股利不是外部入金 |
| 自動 TWR | 每段因子＝（期末淨資產－區間淨入金）÷期初淨資產，幾何串接。出入金保留實際轉帳日收盤後假設 |
| 最大回撤 | 可信 TWR 淨值指數相對歷史峰值的最大跌幅；資料不足則不提供數字 |
| 歷史自訂區間 | 必須有指定起迄日期的確認收盤端點；缺資料不拿今天價格補算 |
| 估值斷點 | 缺資金流日期快照、未確認收盤或無效／重複日期會中斷可信報酬曲線；既有重新起算入口可顯示有效後段 |

持倉報酬、已實現報酬、XIRR 與 TWR 衡量不同對象，本來就可能不同。年度表的帳戶年化報酬反映實際可用端點的期間，不能將不足一年的觀察期間理解為完整曆年實績。

保留使用者原有的收盤後入金假設、手動精確 TWR 計算與資料、原版明暗配色及手機緊湊布局。手動精確 TWR 的一般入口與 AssetTrend 自動績效說明卡維持隱藏。

## 4. 舊資料如何處理

本批不會猜測或批次重寫正式紀錄。以下兩類舊資料可能在更新後顯示待確認，這是品質保護：

1. **舊資產快照**：沒有明確品質標記的快照仍保留，原始資產金額可查看，但不自動當成精確收盤估值。只有核對該日收盤淨資產後，才在快照編輯選擇「已核對當日收盤淨值」。修改日期、金額或自動填值會取消原確認，避免確認沿用到新值。
2. **涉及融資的股票股利**：請依元大實際紀錄填「配股中的融資股數」；明確填 0 表示全數為現股，留空表示尚未確認。分類未確認的配股不作為可出售的現股／融資庫存；若既有賣出依賴這些未確認配股，計算會明確報錯，避免悄悄略過賣出卻增加現金。

純領息年度會顯示收入，但若缺收盤端點，帳戶年化報酬仍可能缺值。新增資料品質判斷不會替使用者補造歷史行情。

## 5. 金鑰與依賴安全改善

### Fugle 後端化

- 新增 `netlify/functions/fugle-proxy.js`。前端現價與歷史資料透過 Firebase 身分驗證後呼叫，金鑰僅從伺服器 `FUGLE_API_KEY` 取得。
- 報價／歷史路徑固定，檢查標的與日期，不接受任意外部 URL；回傳欄位白名單，錯誤不回傳金鑰或供應商原始錯誤。
- 每個實際向上游發出的請求都在伺服器原子預約全域額度；維持每 70 秒最多 55 次啟動及前端合併／排隊，涵蓋跨裝置與函式實例。
- 本機 `.env` 已由舊前端變數移為後端變數。建置檢查確認沒有舊變數、產出 JavaScript 不包含該金鑰值；證據只保存布林值。

**正式環境前提**：本次沒有更改 Netlify 正式設定。部署這批程式前，需要配置伺服器 `FUGLE_API_KEY` 與共用 API 驗證設定，並輪替曾進入前端 bundle 的舊 Fugle 金鑰。僅搬動本機變數無法撤銷既有暴露。未設定新後端金鑰時，報價代理會明確拒絕服務；不會退回前端金鑰。

## 7. 仍保留的能力邊界與發布條件

本批修復確認的邏輯缺陷，以下需求需要獨立設計或正式環境驗收：

- **連續收盤歷史**：自動資產快照仍依賴開啟系統／更新行情；沒有新增後端日終排程，因此關閉系統可能缺日期。
- **備份完整度**：JSON 不含 Storage 圖片／附件二進位原檔；合併還原不是完整時間回溯，跨專案多批次也不是整體原子交易。
- **銀行可用現金**：目前是帳務餘額，沒有完整獨立的逐日 T+2 待交割現金帳。月結 OCR 辨識仍需要使用者核對原單。
- **記住登入**：原有帳號保存與便利性保留；程式內固定衍生 key 的加密不等於獨立密碼保險箱。本批沒有讀取保存密碼或清除帳號。
- **正式服務**：沒有核對正式 Firebase／Netlify 設定、遠端 CI、Google 真實授權、真實行情及付費 AI。沒有讀取私人帳本，不能斷定舊資料已受影響或已完整修復。
- **效能**：build 仍有大於 500 kB 的 chunk，後續可按頁面拆分重量模組。

依專案 `AGENTS.md`，完成本機修正與驗證後，必須取得本批新的明確部署同意，才可一併發布 Netlify／Firebase 或更改正式設定。本報告不代表部署授權。正式驗收應核對新版本、後端金鑰與驗證設定，再以實際元大紀錄確認舊配股分類及重要歷史收盤快照。
