# 瀏覽器可靠性驗收 — 2026-09-08

本輪依照「先驗收資料操作／同步／帳號切換，再清理會影響可靠性的 lint」執行。版本維持同日的 `v26.9.8`。未部署、未修改正式帳號資料、未變更使用者提供的備份；F16、F17 與歷史資料差異繼續暫緩。

## 本輪修正

- 出入金、除權息、任務、專案在儲存期間停用輸入欄位。瀏覽器實際重現舊行為：送出「延遲保存」，等待時改成「儲存期間新輸入」，完成後新輸入被清空，而資料庫只保存原內容。修正後欄位停用，避免產生會被清除的新草稿。
- 出入金、除權息的編輯／刪除按鈕增加可辨識名稱，儲存中停用；任務／專案的取消按鈕、專案顏色與送出按鈕同步停用。
- 任務與專案視窗內直接顯示儲存錯誤；專案讀取失敗不再靜默忽略。任務／專案各自成功載入後清除對應的載入錯誤。
- Google 同步按鈕改用同步設定的 ref 鎖，防止畫面尚未更新前重複啟動；失敗後解鎖，可再次重試。新增測試驗證同時啟動只查詢一次授權，失敗後可重試。
- lint：歷史損益的日期篩選函式改為依日期範圍更新的穩定 callback，補齊 memo 依賴；匯出列元件移至頂層，透過 props 接收忙碌狀態，避免父畫面每次更新都重新掛載元件。

## 隔離方式與可重現步驟

執行 `npm run test:browser:serve`，開啟 `http://127.0.0.1:5184/tests/browser/index.html`。

驗收頁載入正式的 CashFlow、Dividend、TaskManager、useSafeMutation、userDB、investData、plannerData，以及 Google 同步流程；明確的測試 Vite 設定將 Firebase、授權、股票名稱查詢等服務替換為記憶體 fixture。頁面 fetch 只回覆指定的模擬 Google 端點，其他請求直接拒絕。資料留在該頁記憶體中，重新整理即清除。一般開發／正式建置不使用這份設定。

透過「資料情境」選擇正常、延遲、寫入失敗、回覆遺失、讀取失敗；延遲請求由「完成延遲請求」釋放。「檢查隔離資料」顯示 fixture 文件路徑與寫入紀錄。

## 實際瀏覽器操作結果

使用 Codex 內建瀏覽器操作真正的 React 表單與 DOM，結果如下：

| 情境 | 觀察結果 |
| --- | --- |
| 出入金延遲保存 | 修正後金額、備註、日期、類型及送出／列表操作均停用；完成後正常顯示紀錄 |
| 出入金已寫入但回覆遺失 | 錯誤顯示且表單保留；恢復正常後重試使用同一 `id-3`，筆數沒有重複 |
| 出入金編輯與刪除 | 金額 300 更新為 350，仍為同一筆；刪除後由 3 筆降為 2 筆、總額由 650 降為 300 |
| 出入金保存途中切換帳號 | A 的已送出請求完成後只寫入 A 路徑；B 的畫面維持 0 筆，沒有 A 資料 |
| 出入金寫入成功、重新讀取失敗 | 表單清空並顯示「已儲存的紀錄不需再次新增，請重新整理」；清單維持上次成功結果 |
| 任務寫入斷線 | 任務標題保留、失敗提示出現；恢復後可成功新增 |
| 專案寫入斷線 | 視窗內可見錯誤與原名稱；恢復後新增一個專案 |
| 除權息回覆遺失後重試 | 同一 `id-6` 重試，只有一筆除權息紀錄；股票字典與主紀錄一起寫入 |
| Google 流程斷線與恢復 | 模擬 ensure 斷線顯示錯誤；恢復後空事件同步成功 |
| Google 流程延遲時切换帳號 | 收到回覆後停止，顯示帳號已變更；不繼續後續處理 |

Google 項目透過驗收頁按鈕呼叫正式同步函式，並非完整 CalendarHome 的 OAuth 操作驗收。CalendarHome 的同步防重入另以回歸測試驗證。

## 驗證與限制

- `npm test`：260 / 260 通過。
- `npm run build`：通過；仍有既有的大型產物警告。
- 本輪使用服務故障注入，未操作真實 Google 帳號、未測實際 OAuth 回跳、真實網路節流或 Firebase SDK 的離線佇列，也未做所有瀏覽器／手機相容性驗收。因此不將本輪標示為完整端到端上線驗收。
- 全專案 lint 從本輪開始的 61 errors／10 warnings 降為 54 errors／8 warnings；本輪優先處理上述與重繪／日期依賴相關項目，未關閉規則來製造通過結果。
- 前輪的 Firestore／Storage 模擬器 8 項驗證維持原有證據，本輪 UI 修正未重新執行模擬器測試。
