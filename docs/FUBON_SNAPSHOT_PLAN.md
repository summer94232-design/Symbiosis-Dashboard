## 目標與範圍

- 使用者維持元大證券帳務；富邦與富果僅作為行情來源。不新增多券商帳本、下單、成交或庫存同步。
- 保留現有全系統更新範圍，包含歷年已賣出股票；富邦市場快照用於大量台股現價，富果保留單檔補查、歷史 K 線與指數。以資料用途分配來源，不以畫面名稱分配，因儀表板、持倉等畫面共用同一份現價。
- 使用者仍按一次「更新現價」，手機與電腦共用後端，不需各自安裝 SDK 或輸入富邦憑證。
- 不訂閱行情 WebSocket 推播；SDK 登入本身可能建立的連線仍須依官方流程管理。
- 美日股維持既有來源，不受兩家台股行情分工影響。

## 後端架構與選擇條件

建議對前端提供單一、須登入的富邦快照入口；富果既有查詢維持，經共用報價層合併：

`手機／電腦 → 個人系統共用報價層 → 富邦 SDK 市場快照＋富果單檔補查／歷史行情 → 正規化後供各頁使用`

先做 SDK 執行環境驗證，再決定部署位置：

1. 在本機驗證 SDK 安裝、載入與 mock 適配器；取得 API 後才做真正只讀登入與快照。
2. 驗證與 Netlify 相同目標平台的原生套件、打包、憑證檔讀取、呼叫期限及冷啟動耗時。
3. 若單次函式可有界完成登入、查詢與資源清理，且平行執行不會造成登入風暴，可評估 Netlify Functions。不能依賴 warm instance 永遠存在，也不能只用模組變數宣稱跨執行個體去重。
4. 若 SDK 需要穩定長駐 session，採集中式 Node.js 報價服務，由現有後端驗證後轉送，或由該服務直接驗證使用者。單一受控執行個體管理 SDK；擴展時再加入分散式協調。
5. 雲端主機、費用與正式配置在實測後另提具體方案；目前不新增服務、不修改 production。

憑證、API Key、登入 ID 與憑證密碼僅存後端機密設定／受限檔案，不放 VITE_*、前端 bundle、使用者 Firestore 文件、備份或日誌。使用僅行情權限的 Key。若限制 IP，使用後端出口 IP；先確認部署平台是否提供穩定出口。

現有法說會路由有獨立的憑證交換修復，而其他受保護路由曾發生驗證故障。新快照入口必須實測有效登入、失效登入與白名單檢查，不透過略過驗證來接通行情。

## 快照讀取與失敗策略

- 請求僅接受有上限的股票代號陣列，限制格式與長度；不接受任意來源 URL。先驗證個人系統登入與授權，再讀快取或呼叫來源。
- 同時更新請求合併為同一輪市場讀取。市場回應快取初始建議 10 秒，可依量測調整；快取重用保留原始取得時間，不能標成剛取得。
- TSE、OTC 各查一次後按清單篩選；不能保證兩次即涵蓋全部股票、指數與市場。
- 一個市場失敗不丟棄另一市場成功結果；缺價、停牌、格式錯誤分開記錄。
- 缺漏代號可使用既有富果查詢補足。初始建議每輪自動補查最多 10 檔，其餘顯示未更新，避免富邦故障時悄悄退回上百檔慢查。此值屬待實測的產品設定。
- 富邦整體登入／權限故障時顯示原因及「改用富果更新」選項；使用者選擇後沿用富果 55 次／61 秒排隊規則，顯示預估等待與進度。不自動循環切換或大量重試。已成功的富邦市場結果不因另一市場失敗而被覆蓋。
- 富邦和富果都回傳同一代號時，先檢查來源日期、有效成交／試撮狀態及時間戳，再選擇結果；不能固定以某一家覆蓋另一家。保存每檔來源供診斷，畫面平常不需展示冗長資訊。
- 429 遵守供應商等待要求；設定整輪截止時間，等待超出前景期限時回報可重試狀態。5xx／暫時網路錯誤有限次重試，無效金鑰或憑證不連續重登。
- SDK 登入與重連也須去重、有退避與有界等待。定時器無法取消 SDK 原生操作時，不得因 UI 逾時就再啟動另一組登入；須用可隔離的 worker／程序或 SDK 支援的取消方式管理。
- 診斷記錄市場、耗時、命中快取、補查數與固定錯誤分類；不記錄密鑰、憑證、token 或原始登入回應。

## 資料與績效正確性

「市場行情快照」與本系統「每日投資資產快照」不同，前者成功不表示已取得精確收盤估值。

- requestedAt：本輪請求时间；fetchedAt：實際來源取得时间。重用快取時不更新 fetchedAt。
- sourceDate：來源 date，不以今天補填。sourceUpdatedAt：驗證單位及語意後才正規化，不能把微秒直接當毫秒。
- 價格必须為有限正數。缺價不填零、不用成本冒充最新價格。
- 不能直接把 lastPrice 當正式成交價，因文件明示可含試撮。明確 `isTrial: true` 的回應不採價；`isTrial` 省略時不把 lastPrice 當確認成交價。
- 一般快照可用的 `closePrice` 僅映射為 `reference`，可供即時顯示，但名稱本身不是當日最終收盤的證據；既有自動每日資產快照會將 `reference` 判為不合格，不把它當精確收盤估值。
- 若快照時間是整個市場批次時間，不當作每檔成交時間。跨富果／富邦來源比較需確認時間語意，避免舊資料被錯認為較新。
- 休市回傳上個交易日資料時保留來源日期；不能以本次下載成功宣告當日收盤資料完整。
- 保留手動 exact TWR、既有帳務資料、盤後實際入金日期假設及現有收盤快照保護。

3. 檢查價格、日期、時區、時間戳單位、試撮與無成交情境；和相同時間附近的富果結果比較，容許合理的取樣時間差。先確認 ETF、歷年已賣出代號及特殊市場的實際涵蓋率，再定補查上限。
4. 驗證登入失效、重啟、網路中斷與多個前端同時按更新；不為測試故意對正式 API 大量打到限流。
5. 完成選定雲端環境的冷啟動、平行執行與授權測試。合成測試通過不等於已驗證這一步。
6. 在相同清單上量測原富果全單檔與「富邦市場快照＋富果有限補查」的完成時間、各來源請求數與有效價格比例。暖快取與冷登入分開報告，不預先保證秒數或倍數。
7. 完成本機驗證及具體發布方案後，等待使用者批准才部署。本批舊部署批准不適用。
8. 保留現價主要來源設定切回富果的能力；正式切換或回復正式配置均需符合專案部署批准要求，不重寫歷史帳務／績效資料。

成功條件：全系統清單完整、有來源時間與失敗提示、手機／電腦無需富邦互動登入、憑證不進前端、無交易能力接入、正式來源與部署環境驗證通過。

## 2026-09-24 部署前檢查

- `fubon-snapshot` 改用 Netlify 現代 `Request`／`Response` 函式格式；`netlify.toml` 對此函式指定 `esbuild`，並將含原生 `.node` 模組的 `fubon-neo` 設為外部套件。本機官方打包工具 15.5.1 實際使用 nft 打包現代函式；壓縮檔已確認包含 `fubon-js.linux-x64-gnu.node`、SDK 與行情依賴，未包含 `.pfx`／`.p12` 私人憑證。雲端實際載入仍待驗證。
- `.pfx` 在本機由路徑讀取；雲端以 `FUBON_CERT_BASE64_1`／`FUBON_CERT_BASE64_2` 兩個後端機密設定提供，避開單一值 5000 字元限制，函式在系統暫存目錄建立權限限制的隨機檔案。舊式 Netlify Lambda handler 另有總環境變數 4 KB 限額。為避免共用 Functions 範圍變數影響其他路由，10 個既有入口也已透過共用 Request／Response 適配器改成現代格式；原有驗證、查询參數、JSON、OAuth 重新導向與回應狀態保持原行為。官方打包結果確認全部 11 個入口 runtime API v2。
- 分段修正與後續相容修復仍屬尚未正式發布的 `v26.9.24.3` 同一批次。欄位長度依據：[Netlify 環境變數限制](https://docs.netlify.com/build/environment-variables/overview/)。
- 最終本機驗證：477 項測試通過，lint、TypeScript／Vite 正式建置通過；11 個後端官方打包通過。新增入口測試涵蓋未授權拒絕、JSON／查詢參數、OAuth 導向及 CORS 預檢。草稿的相容問題已修正並通過雲端入口檢查，但尚未正式部署或啟用；未把本機合成測試視為雲端實際登入成功。
- 現在仍缺雲端冷啟動、授權檢查與只讀行情驗證。先前官方工具下載失敗，後來找到電腦已有快取，已完成本機正式打包檢查。使用者已自行填妥五項富邦機密，唯讀 API 確認皆存在於 Production 且包含 Functions 範圍；Netlify 隱藏機密值，因此不能透過此查詢證明實際登入資料正確。正式旗標維持關閉，部署與啟用仍待使用者對完整批次明確批准。
- 現有後端一次最多接受 3000 個代號，只向富邦請求 TSE、OTC 各一輪並在回應中過濾。這個上限尚需以實際全系統清單確認；前端對未覆蓋的代號只做有限富果補查。快照故障、部分市場失敗的精簡提示與手動全富果重試仍待完成。
