# 個人整合管理系統建置企畫書

日期：2026 年 9 月 30 日  
參考系統：Symbiosis 個人系統  
用途：規劃個人管理系統，也可直接交給 AI 協助設計與開發。

## 1. 企畫目標

建立一個由自己掌握資料、能在手機與電腦使用的個人管理網站，把筆記、任務、行程與需要的投資資訊放在同一個入口。功能、名稱、介面與分類依使用者生活方式調整。

參考 Symbiosis 的三大領域：

- **知識管理**：保存學習筆記、文章、圖片與文件，透過標籤和連結找回資訊。
- **行事曆與任務**：整理待辦、專案、截止日與重要事件。
- **投資管理**：記錄交易、持倉、資金與投資研究；沒有投資需求時可以完全不做。

例如：研究某家公司時，先建立研究筆記，再建立法說會事件和「閱讀財報」任務；實際買入後，交易紀錄連回當初的研究，日後可復盤。以學習為主的人，則可以把同樣的關聯用在課程、讀書筆記、作業和考試。

本企畫參考原系統的本機程式、頁面路由、依賴與操作手冊；原系統本機版本與線上部署進度可能不同。下列「參考系統功能」是功能盤點，「新系統建議」是新專案設計，不表示每一項已在原系統上線。

## 3. 參考功能與優先順序

「第一版」是預設建議；若投資是主要目的，可以把基礎交易與持倉移到第一版。

### 3.1 共用基礎

| 功能 | 參考系統已有的能力 | 新系統建議 |
|---|---|---|
| 登入與資料隔離 | Firebase 登入、依使用者分開保存資料 | 第一版；先採單一登入與單一 Firebase 專案 |
| 總覽 | 投資概況、近期行程、未完成任務 | 第一版；依用途顯示今天要看的內容 |
| 手機介面 | 緊湊版面、短操作、手機導覽 | 第一版；兼顧直向、橫向與觸控 |
| 設定與版本 | 個人設定、主題與版本顯示 | 第一版 |
| 匯入與匯出 | CSV、Excel、JSON，依模組提供 | 第一版先做 JSON 備份；其他格式後續加入 |
| 備份還原預覽 | 顯示新增、覆蓋與保留資料的差異 | 第一版；明確說明合併或取代的行為 |
| 資料健康檢查 | 找出部分帳務、筆記關聯與資料異常 | 後續；先具備輸入驗證與錯誤提示 |

### 3.2 知識管理

| 功能 | 能做什麼 | 新系統建議 |
|---|---|---|
| 筆記 | 建立、編輯、刪除、搜尋文字與網址筆記 | 第一版 |
| 富文字與附件 | 排版、貼圖、上傳圖片或文件 | 第一版可先用文字；附件另列一個里程碑 |
| 分類與標籤 | 階層標籤、篩選與排序 | 第一版先做一般標籤，階層與拖曳後續加入 |
| 筆記模板 | 原系統有交易日誌、選股分析、法說會筆記 | 換成自己的模板，如會議、讀書、專案紀錄 |
| 筆記互相連結 | 保存相關筆記與反向連結 | 第二階段 |
| 知識圖譜 | 用節點與線查看筆記、標籤關係 | 選配；筆記數量與關聯夠多再做 |
| AI 標籤與相關筆記 | AI 提出分類、相關筆記建議 | 選配；使用者確認後才採用 |
| 垃圾桶 | 刪除後可復原、永久刪除 | 第一版 |
| 筆記匯出 | TXT、Markdown，可手動交給 NotebookLM 等工具 | 第二階段；不預設自動傳送 |

第一版搜尋必須說明涵蓋範圍。若只搜尋已載入的筆記，就應標示「目前載入資料」；要搜尋所有正文，需另外設計全文搜尋服務或索引，不把一般資料庫查詢當作完整全文搜尋。

### 3.3 行事曆與任務

| 功能 | 能做什麼 | 新系統建議 |
|---|---|---|
| 月曆與日期明細 | 查看日期、當日事件、新增與編輯行程 | 第一版 |
| 任務 | 標題、完成狀態、優先級、截止日與備註 | 第一版 |
| 專案與任務分類 | 依專案、標籤、狀態篩選與排序 | 第一版先做簡單專案 |
| 任務進月曆 | 有截止日的任務連到月曆和今日總覽 | 第一版 |
| 每日重點 | 原系統整合行程、任務與財經新聞 | 第一版先做行程與任務，新聞選配 |
| Google Calendar | 原系統手動事件可雙向同步，財經事件以單向同步為主 | 後續先做手動單向匯出，再設計雙向同步 |
| 財經事件 | 法說會、除權息、FOMC、期貨結算等 | 有投資需求才加入 |
| 年度資料維護 | 由後端排程查核官方年度資料 | 有相應資料來源時再加入 |

新系統先約定全天事件、具體時間、時區與重複事件的資料格式。雙向同步要另訂衝突、刪除、重試與防重複規則，不能只靠「最後修改時間較新」就覆蓋所有資料。

### 3.4 投資管理（依需求選配）

| 功能 | 參考系統能做什麼 | 建議順序 |
|---|---|---|
| 買賣紀錄 | 買賣、手續費、交易稅、整股與零股、匯入 | 基礎投資版 |
| 持倉 | 股數、成本、均價、市值、配置與損益 | 基礎投資版 |
| 出入金與股利 | 記錄實際資金流、現金與股票股利 | 基礎投資版 |
| 自選股 | 保存關注標的與研究欄位 | 基礎投資版 |
| 資產趨勢 | 資產快照、報酬曲線與指數比較 | 帳務與價格資料可靠後 |
| 歷史損益與年度復盤 | 已實現損益、月年統計、勝率與持有期間 | 帳務計算驗證後 |
| 對帳核對 | 以券商月結資料比對交易與費用 | 依自己的單一券商格式設計 |
| 融資管理 | 本金、利息、維持率與壓力測試 | 有融資需求才做 |
| 組合水位試算 | 依目標水位與占比試算調整交易 | 進階；與真實帳本隔離 |
| 觀點追蹤 | 紀錄看法、理由、目標價與事後結果 | 進階 |
| 賣出追蹤 | 檢查賣出後不同期間的價格變化 | 進階 |
| 產業地圖與脈絡 | 公司分類、供應與合作關係圖 | 進階 |
| 當沖處理 | 配對與相關費稅、例外情形 | 有實際需求才做 |

原系統交易帳務以使用者的元大證券帳戶需求為基礎。新系統應先確認自己使用的單一券商、市場與費率，不需要先做多券商架構。原系統程式中也有 Fugle、富邦行情快照與海外報價相關整合；行情來源與實際交易券商是不同角色，不能把行情串接當作券商帳戶連線或自動下單。

第一版投資管理可以手動輸入參考價格，不必先取得即時行情 API。交易紀錄和試算不會自動送出任何委託。

## 4. 推薦建置架構與工具

建議採用與參考系統接近的網站架構，方便 AI 分步開發和日後維護。以下是設計建議，不是唯一選擇。

| 工具／平台 | 白話用途 | 是否需要 |
|---|---|---|
| AI 開發工具，例如 Codex | 協助寫程式、檢查、除錯；要讓工具能存取自己的專案資料夾 | 建議選一套作為主要開發工具 |
| Git + GitHub 私人儲存庫 | 保存程式版本、比較修改、回復舊版 | 建議從第一天使用 |
| Node.js + npm | 在電腦安裝套件、啟動與建置網站 | 本機開發需要；版本依 Vite 官方要求選定 |
| React | 製作頁面、表單、清單與互動元件 | 預設採用 |
| TypeScript | 定義資料欄位，提早發現部分程式錯誤 | 預設採用 |
| Vite | 啟動開發網站、產生上線所需檔案 | 預設採用 |
| Firebase Authentication | 處理登入；可選 Email 或 Google 登入 | 雲端正式版需要 |
| Cloud Firestore | 保存筆記、任務、事件等資料 | 雲端正式版需要 |
| Cloud Storage for Firebase | 保存圖片與文件實體檔案 | 有附件才需要 |
| Netlify | 託管前端網站、提供 HTTPS 與部署流程 | 預設網站平台 |
| Netlify Functions | 在後端呼叫 AI 或外部 API、驗證登入、保管秘密金鑰 | 有外部服務時需要 |
| Google Calendar API | 讀寫 Google 行事曆事件 | 同步功能選配 |
| Gemini API 或其他 AI API | 在系統內提供摘要、標籤或相關筆記建議 | 選配；先選一個供應商 |
| 行情／新聞資料 API | 取得價格或新聞 | 投資進階版選配 |

Codex 官方定位是協助寫程式、審查和除錯的開發代理。使用 AI 開發工具，與在網站內呼叫 AI API，是兩個分開的需求；本企畫不要求第一版內建 AI。[OpenAI 官方說明](https://developers.openai.com/api/docs/guides/code-generation)

React、TypeScript 和 Vite 分別負責介面、型別與開發建置。新專案應由 AI 查核套件相容性後固定版本，保留 lockfile。[React](https://react.dev/)、[TypeScript](https://www.typescriptlang.org/docs/)、[Vite 入門](https://vite.dev/guide/)

Firebase Authentication 負責登入；Firestore 保存雲端文件，搭配權限規則限制誰能存取資料。[Authentication](https://firebase.google.com/docs/auth)、[Firestore](https://firebase.google.com/docs/firestore)

Netlify Functions 是處理事件與請求的伺服器端程式，適合在本方案中作為外部 API 的代理。[Functions 官方說明](https://docs.netlify.com/build/functions/overview/)

參考系統也使用 Tailwind CSS、Tiptap、Recharts、D3 與 Lucide 等套件處理樣式、富文字、圖表、圖譜和圖示。新系統可按需求選用；第一版不需要把所有套件都裝進去。

## 5. 簡化資料設計

參考系統目前分成投資／行事曆與知識庫兩個 Firebase 專案。從零開始建置時，建議先在**一個 Firebase 專案使用一套 Auth**，減少跨專案帳號對應和設定。

概念架構：

```text
手機／電腦瀏覽器
  └─ React 網站（Netlify）
       ├─ Firebase Authentication：登入
       ├─ Cloud Firestore：個人資料
       ├─ Cloud Storage：圖片與附件（選配）
       └─ Netlify Functions：驗證使用者後呼叫外部服務
            ├─ AI API（選配）
            ├─ Google Calendar API（選配）
            └─ 行情／新聞 API（選配）
```

建議資料集合：

| 集合 | 主要內容 |
|---|---|
| `users/{uid}/notes` | 筆記標題、標籤、類型、摘要與時間 |
| `users/{uid}/noteBodies` | 筆記正文、富文字內容與附件引用 |
| `users/{uid}/tasks` | 任務、優先級、截止日、狀態與專案 ID |
| `users/{uid}/projects` | 專案名稱與分類 |
| `users/{uid}/events` | 全天或定時事件、時區與來源 |
| `users/{uid}/trash` | 可復原的刪除紀錄 |
| `users/{uid}/settings` | 偏好、主題與非秘密設定 |
| 投資選配集合 | `trades`、`cashflows`、`dividends`、`watchlist`、`assetSnapshots` |

附件路徑綁定 UID 和筆記 ID，並保存檔名、大小、型別及 Storage 路徑。Google refresh token 和其他秘密憑證另外存放於受後端限制的憑證儲存位置，不放入一般設定匯出。

資料關聯使用穩定 ID。已完成任務是否還顯示在月曆、刪除筆記後如何處理連結、專案刪除時任務是否保留，都需先訂清楚。

大量筆記採摘要分頁，開啟文章才載入正文和附件。設定查詢筆數、快取與失效規則，避免每個頁面反覆下載全部資料。

## 6. 帳號、設定與費用

### 準備順序

1. 建立自己的專案資料夾與 GitHub 私人儲存庫。私人／公開屬性可在建立儲存庫時選擇。[GitHub 官方說明](https://docs.github.com/en/repositories/creating-and-managing-repositories/creating-a-new-repository)
2. 在自己的電腦設定 AI 開發工具、Node.js 與 npm，先啟動本機樣板。
3. 使用自己的 Google 帳號建立 Firebase 專案，設定登入、Firestore 與權限規則。
4. 需要附件時，再設定 Storage、檔案限制與計費。
5. 建立自己的 Netlify 網站，準備環境變數、路由和正式網址。
6. 需要 Google Calendar 時，設定 Google Cloud 的 Calendar API、OAuth 同意畫面、測試使用者與回呼網址；只索取功能必要的權限。Calendar API 可處理行事曆及單次／重複事件。[Google 官方說明](https://developers.google.com/workspace/calendar/api/guides/overview)
7. 最後加入 AI／行情 API；全部帳號、金鑰與資料由自己管理。

AI 可以先用模擬資料完成介面。遇到必須由本人登入或啟用計費的步驟，應提供畫面位置和設定清單，保留已完成的本機成果。

### 費用原則

不承諾「永久免費」。開發工具訂閱、網站託管、資料庫、附件儲存、外部 API 和網域要分開計算。

| 項目 | 規劃方式 |
|---|---|
| AI 開發工具 | 依自己採用工具的訂閱與額度查核 |
| 網站與後端函式 | 查核 Netlify 所用方案，監控流量、部署與函式用量 |
| Firestore | 依讀取、寫入、資料大小和實際方案估算 |
| 圖片與文件 | 控制單檔上限、壓縮圖片、產生縮圖和清理未使用檔案 |
| 系統內 AI | 限定使用者按下按鈕才呼叫；限制文字長度和頻率 |
| 行情與新聞 | 先確認方案、資料使用條款、呼叫頻率與授權 |
| 自訂網域 | 選配；另查註冊及續約價格 |

截至本企畫查核日期，Cloud Storage for Firebase 需要 Blaze 按用量計費方案；Blaze 仍有免費用量，但需連結 Cloud Billing，實際費用依地區和用量而定。[Firebase Storage 官方計費要求](https://firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024)

Netlify 的新計費方案以 credits 衡量使用量，也仍有舊方案；必須確認自己帳號適用的方案，依該方案的額度推估費用。[Netlify 方案說明](https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/credit-based-pricing-plans/)、[Functions 計費](https://docs.netlify.com/build/functions/usage-and-billing/)

建議先定每月預算、啟用用量通知，並在系統設定 API 呼叫與檔案上限。預算通知本身不等於硬性停止扣款；不願啟用計費時，第一版先做文字筆記，延後附件功能。

## 7. 資料保護與復原要求

以下應直接納入規格，讓 AI 在開發時一起完成。

- 未登入不能讀取私人資料；前端之外，Firestore、Storage 與後端 API 都要檢查存取權限。
- 不保存使用者的明文或可逆密碼；登入交給 Auth。服務帳號金鑰、AI API key 與 OAuth secret 放在後端秘密設定，不寫入前端程式、Git 或一般備份。Gemini 官方要求正式客戶端避免曝露 API key，使用後端代理。[官方金鑰安全說明](https://ai.google.dev/gemini-api/docs/api-key)
- 切換帳號或登出時清除私人快取；匯入和還原綁定開始操作的使用者，帳號變動就中止。
- JSON 備份保存原始欄位、文件 ID 與備份格式版本；Excel／CSV 報表另提供，不拿報表代替復原備份。
- 明確區分「資料備份」和「附件備份」。第一版若只含附件引用，要直接顯示不含實體檔案；加入附件時規劃檔案包、清單與還原核對。
- 還原前預覽差異、保存現有備份，確認後才寫入。說明合併／取代規則、部分成功和重試方式，不承諾跨服務整份原子還原。
- 筆記刪除先進垃圾桶；永久刪除另行確認。專案刪除若會連帶刪除任務，先顯示影響筆數。
- 檔案匯入先驗證格式、日期、金額與重複 ID；失敗要保留原因及已確認成功筆數。
- AI 功能預設由本人手動觸發，只傳必要內容；AI 回覆是待確認建議，不直接覆寫資料或執行交易。
- 列表和表單具備載入、空資料、失敗和重試狀態；「已同步」只在確認寫入成功後顯示。

## 8. 介面設計

第一版導覽建議：**總覽、筆記、任務、月曆、設定**；開啟投資模組後再加入投資入口。

- 繁體中文、熟悉的名稱和明確動詞；說明文字只放使用者做決定需要的資訊。
- 手機預設資訊密度高：縮小不必要的留白、卡片內距和列高，短操作保持同列。
- 按鈕仍需容易點擊，文字可讀，金額、日期和重要狀態不能因版面緊湊而消失。
- 月曆格可用色點表示事件，點日期看完整列表；手機表格可橫向捲動或改成摘要列。
- 低頻匯入、匯出等操作放在「更多」或設定中；錯誤和未儲存內容要保留可見。
- 支援桌面、手機直向與橫向；主題切換可放後續版本。

## 9. 分階段執行計畫

用驗收成果管理進度，工期由實際需求和試作結果再估，不先保證幾天完成。

| 階段 | 交付成果 | 完成條件 |
|---|---|---|
| 0：需求與頁面設計 | 需求表、功能範圍、導覽、資料關聯、帳號與費用清單 | 清楚列出第一版做哪些功能 |
| 1：本機原型 | 可啟動的網站、總覽、筆記、任務與月曆，以模擬資料展示 | 手機和電腦可操作；標明尚未接雲端 |
| 2：可用第一版 | 真實登入、資料保存、標籤、垃圾桶、JSON 備份與還原預覽 | 重整及跨裝置仍可取得資料；權限與復原測試通過 |
| 3：個人化擴充 | 附件、模板、筆記連結、Google Calendar 或基本投資模組 | 每次只加入一組需求並完成驗收 |
| 4：進階自動化 | AI 輔助、全文搜尋、圖譜、報價、復盤、排程 | 有明確需求、費用控制與失敗復原方式 |
| 5：正式發布 | 操作手冊、檢查紀錄、部署清單、回復方式 | 本機驗證完成，由本人批准該批次正式部署 |

新增功能後先完成本機驗證，再申請本次批次的部署批准。正式網站、Firebase 規則和正式設定的修改都列在同一張發布清單；GitHub 連線若會自動發布，也需在流程中控制正式分支和發布時機。

## 10. 驗收清單

- [ ] 在自己的電腦依 README 可以安裝和啟動。
- [ ] 登入後可新增一篇筆記，重整後正文、標籤與時間一致。
- [ ] 建立有截止日的任務，會出現在正確日期；完成後依規格更新總覽和月曆。
- [ ] 全日事件不會因時區變成前一天，定時事件以選定時區顯示。
- [ ] 未登入者無法讀寫私人資料；如支援多帳號，A 無法讀寫 B 的資料。
- [ ] 網路或服務失敗時保留輸入，顯示原因與可用的重試操作。
- [ ] 刪除筆記後能從垃圾桶復原，關聯資料符合規格。
- [ ] 匯出測試資料，再於隔離測試環境還原，核對 ID、欄位、正文與關聯。
- [ ] 如有附件，實際檔案可取回；備份介面準確說明包含範圍。
- [ ] Google 同步如有啟用，重試不重複建立，衝突與部分失敗有結果摘要。
- [ ] 手機直向、橫向與電腦可以閱讀、輸入和執行主要操作。
- [ ] 套件建置、型別檢查，以及受影響邏輯的測試通過；驗證範圍有記錄。
- [ ] 正式上線使用本人帳號和自己的測試／正式設定，沒有沿用參考系統的私人資料或憑證。

## 11. 有投資需求時的額外規格

1. 以交易與股利紀錄推導持倉，保留穩定的同日交易順序，禁止超賣。成本法、費率與捨入方式要明確。
2. 使用實際轉帳日期記錄出入金。參考系統預設收盤後入金；使用者應確認自己的使用情境，不由 AI 回填到買股日期。
3. 每筆價格保存來源、來源時間、價格日期和類型；缺價或過期時明確標示。成本代替估值時不能顯示成即時市價。
4. 基礎持倉、股利、資金與對帳先正確，再做績效。近似 TWR、精確 TWR、XIRR 與單純盈虧不能混成同一指標。
5. 盤中價格和未核實的舊快照不能標成精確收盤估值；資料不足時顯示無法計算或近似。
6. 現金股利以實際入帳、股票股利以實際配發日影響帳本；避免把公告直接當成已收到。
7. 水位和壓力試算使用獨立資料，不能修改真實交易。融資、交割假日與當沖規則按自己的市場和券商確認。
8. 使用小型可人工核對的案例測試：買入、分批賣出、費稅、股利、出入金與超賣；結果與券商資料核對。

## 12. 交給 AI 的方式

將本企畫書全文提供給能操作自己專案的 AI，並貼上以下指令。另附的 `PERSONAL_SYSTEM_AI_BRIEF.md` 是可獨立使用的精簡開工指令。

```text
請依照附上的「個人整合管理系統建置企畫書」，協助我建立屬於自己的系統。

先讀取我填寫的需求表。若尚未填寫，最多先問 5 個會影響第一版的重要問題，將其他項目列成可調整的預設。

請用繁體中文溝通。先交付第一版功能範圍、頁面配置、資料結構、平台與費用條件、分階段工作清單和驗收方式。

預設使用 React + TypeScript + Vite、單一 Firebase 專案的 Authentication 與 Firestore、Netlify；需要外部 API 時才加後端 Functions。附件、AI、Google Calendar 和投資是選配。

若我已提供專案資料夾且允許你開發，請接著建立可在本機運作的第一版，不要停在泛泛建議。沒有真實雲端設定時，先用明確標示的模擬資料，並列出本人要完成的設定；不要將模擬模式說成雲端功能已驗證。

採用手機資訊密度高但好閱讀、好操作的版面。資料要依 UID 隔離，不能保存可逆密碼或把秘密金鑰放在前端。先完成筆記、任務、月曆、垃圾桶、JSON 備份和還原預覽。

每個階段請交付實際檔案、啟動方式、操作說明、驗證結果與尚未完成項目。只跑與變更相關的驗證；共用登入或資料結構改動時擴大測試。

所有正式部署、正式 Firebase 規則或正式設定變更，先完成本機成果與驗證、列出本次發布清單，再等我明確批准。先前批准不適用後來的新批次。不要從參考系統帶入私人資料、帳密或憑證。
```

## 13. 後續與 AI 合作的簡短指令

**增加功能：**「請先列出這個功能會影響的頁面和資料，再完成本機實作、相關驗證與操作說明，正式部署等我批准。」

**修改介面：**「請讓手機畫面更緊湊，保留重要內容和可點擊的操作；用手機直向與橫向檢查主要流程。」

**修正錯誤：**「預期結果是……，實際結果是……，操作步驟是……。請找出原因、修正並驗證受影響功能，列出仍未驗證的部分。」

**準備發布：**「請整理本次功能、驗證結果、環境變數、權限規則、費用影響與回復方式，完成後等待我的發布批准。」

本企畫最適合先做一個每天會使用的小版本，再以自己的使用紀錄決定下一批功能。
