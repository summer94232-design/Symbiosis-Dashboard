# 報價額度預約去重

版本：`v26.10.1.4`。已完成正式發布與驗證，見 [發布紀錄](RELEASE_2026-10-01.md)。

## 問題與結果

原本每個批次先按自己的代號數預約額度，實際抓報價才共用正在查詢的股票。隔離重現中，同一裝置同時查相同 20 檔的兩個批次，會預約 40 次但只實際呼叫 20 次，剩餘額度被不必要的預約占用。

現在先同步登記整個批次真正新增的股票，包含尚在排隊的代號，再預約額度。同時進來的批次或單檔查詢直接共用已登記的 Promise；共用結果仍各自保留呼叫者的 `requestedAt` 與實際取得資料的 `fetchedAt`。

| 情境 | 本次結果 |
|---|---|
| 兩批相同 20 檔，第一份額度回應還沒到 | 只申請 20 次，實際查 20 次 |
| 兩批各 20 檔、重疊 10 檔 | 分別申請 20、10 次，實際查 30 次 |
| 單檔查詢與批次相同股票同時執行 | 共用請求，不另占額度；先後順序皆涵蓋 |
| 批次中的股票已查好，其他股票仍在等待 | 後來的查詢共用已完成結果，不新增預約、不改寫成較新的取得時間 |
| 預約失敗或只取得部分額度 | 所有共用呼叫都收到結果；批次完成後釋放登記，可再次查詢 |
| 共用請求需要重試 | 只有實際新增的重試申請額度，原本共用者不另申請 |

這是同一頁面執行環境的重複預約修正。不同裝置有獨立的前端請求，仍透過原有伺服器 transaction 合計限制為 55 次／70 秒；本次沒有加入跨裝置報價結果快取或提高流量上限。原有批次最多 5 個 worker、8 秒報價預算、429 冷卻及歷史下載限制保留。

## 驗證

- 143 項相關測試通過，涵蓋富果報價／歷史行情、價格日期安全、全系統刷新、混合行情及額度控管。
- 其中前端接實際額度計算函式的隔離測試確認：重複 20 檔後伺服器只留下 20 個預約，剩下 35 個仍可用；總數到 55 後不再發送新報價。
- 程式檢查與 production build 通過。測試以假報價與記憶體資料庫執行，沒有使用正式 API 額度或寫入正式資料。
- 紀錄：`log/quote-reservation-dedup-tests.txt`、`log/quote-reservation-server-tests.txt`、`log/quote-reservation-dedup-build.txt`。

登入憑證等待的整段逾時、API 金鑰後端化及套件更新屬其他建議項目，本批未修改。
