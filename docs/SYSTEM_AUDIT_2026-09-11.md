本次檢查目前工作目錄的實際程式碼，包含先前尚未提交的修改。工作跨越台北時間午夜，顯示版本統一更新為 `v26.9.11.1`。沒有部署、沒有操作正式帳戶，也沒有修改使用者的歷史帳務資料。

## 結果

確認並處理 **7 類問題**。原有 329 項測試全數通過，但沒有涵蓋下列跨功能情境；因此不能只用原有測試通過推論整個系統沒有邏輯錯誤。

| 編號 | 優先級 | 確認問題與影響 | 本次處理 |
|---|---|---|---|
| A01 | P1 | 修改／刪除較早買入或配股，可能讓後續賣出變成超賣；持倉略過該賣出，現金仍計入賣款 | 交易編輯／刪除、股利編輯／刪除、月曆刪除股利加入伺服器帳本預檢，阻擋新增或加重股數缺口。詳見保護範圍 |
| A02 | P1 | 健康中心把預告配股、尚未到配發日的股數算入庫存，漏報超賣；實際持倉使用另一套規則 | 排除預告、使用實際配發日、明確配發日當日先配股；交易排序改用共用函式 |
| A03 | P2 | 月曆有顯示跨日行程，每日簡報及儀表板卻只看開始日期，第二天起漏顯示 | 保留起訖資料，共用日期交集判斷；午夜結束的行程不算入下一天 |
| A04 | P2 | 每日簡報把所有手動事件的類型改成個人，科技／股東會等標籤與月曆不同 | 保留原始類型，僅舊資料缺少類型時預設為個人 |
| A05 | P2 | 未勾選個人同步、只同步科技等類型時，仍匯入 Google 原生個人事件；已連結但類型未勾選的事件也可能重複匯入 | 原生個人事件遵守個人同步開關；連結反查涵蓋完整本機集合，避免把排除類型當作全新事件 |

| A07 | P2 | 精確 TWR 把同秒順序 `1`／`01` 當作不同值，但排序又把兩者當成相同數字，結果受輸入順序影響 | 重複檢查先轉數字，拒絕數值相同的同秒順序 |

P1 是帳務／資料完整性優先問題；P2 是特定情境下的功能一致性問題，不代表已確認正式資料受損。

## A01 的重現與保護範圍

修正前執行實際 `Trades.handleSave`，僅以記憶體函式替代資料庫與 UI：

1. 9/1 買入 1,000 股，每股 100；9/2 賣出全部 1,000 股，每股 110。範例費稅為零以隔離股數問題。
2. 把 9/1 買入改為 500 股、收付 50,000。
3. 原程式接受寫入並顯示成功。後續可賣僅 500 股，卻已有 1,000 股賣出。
4. `calcPositions` 剩 500 股、已實現損益列為零筆；`calcAvailableCash` 仍加上 110,000 賣款。若初始入金 100,000，現金變成 160,000。

修正後，相同 UI 案例在寫入前阻擋，顯示缺少 500 股，保留表單。配股刪除、減量、延後或改回預告也會檢查後續賣出。正常價格修正、現金股利更正、改善既有股數缺口的操作仍可進行。

**邊界：這是互動編輯／刪除入口的伺服器資料預檢，不是整本帳務的跨裝置原子交易。** 預檢後到寫入間，另一裝置仍可能新增或修改紀錄。本批沒有改造 CSV 匯入、備份還原及直接 Firestore 寫入為統一帳本交易，也沒有自動修補已存在的不合法帳務。這些入口和同時寫入情境仍須另外處理；不能宣稱帳本完整性已由後端全面保證。

## 檢查方式與證據

- 人工追蹤投資帳務／持倉／健康中心、月曆／簡報／儀表板／Google 同步、KMS 搜尋索引與備份資料流；對照先前修正文件與現有測試。
- 新增 `tests/system-integration-audit.test.mjs`，直接執行原始純函式及頁面操作函式，僅替換遠端 I/O／狀態接收端。
- 第一批 6 個案例在修正前全數失敗；健康中心另重現預告配股與配發日期錯置。歷史帳務使用實際 UI 儲存函式確認原先確實接受錯誤修改。
- 新增回歸測試已加入 `npm test`。不是只比對程式文字，也不把確認缺陷的 assertion 當成正確性測試。
- 本次沒有逐一點擊所有正式頁面；Google 使用隔離回應，不代表真實 OAuth、正式 Functions、雲端索引部署或供應商 API 已驗收。
